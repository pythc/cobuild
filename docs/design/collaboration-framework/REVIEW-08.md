## 1. 结论

下一批建议补 D3 的最小入口：在现有项目概览增加只读代码状态，使用项目已有的仓库链接，读取公共 GitHub 仓库的近期合并请求及指定提交的检查结果。通过一个实际来源检验接口边界，不先建设完整连接器平台。

首批只支持公共仓库是刻意缩小的验证范围，不代表已解决企业私有仓库接入。私有仓库需要另行落实凭据存储、仓库授权范围、用户可见性及撤权；当前项目组织内可见，不能直接拿管理员令牌给全员展示私有仓库内容。

## 3. 建议最小实现

### 3.1 一份只读来源接口

- 放在现有平台服务内，复用项目概览的按来源读取方式，不增加服务、数据库或依赖中间件。
- 提供两个小接口：读取仓库/近期合并请求；按指定合并请求的 head SHA 读取检查。先实现 GitHub，其他提供方仅保留同样的输入输出边界，不写空实现。
- 本地项目仍按 project ID 识别；来源引用包含 provider、host、repository ID、PR ID/编号和 head SHA。仓库链接用于显式选择，不以项目名或仓库名猜测需求关联。
- 不写 Delivery 主表，不把实时查询结果当成固定版本的交付验收记录；后续 Delivery 才持久绑定提交和制品。

### 3.2 现有项目页增加一处信息

- 项目概览显示仓库、近期少量合并请求、草稿/打开/关闭/已合并状态、原站链接和读取时间。
- 用户展开某项后才读取检查；结果必须标注对应 SHA。head 变化后旧检查不得冒充新提交的结果。
- 检查需区分失败、运行中、未发现、部分结果与不可用；合并不等于部署，检查成功不等于上线。
- 沿用项目/页签状态和失败隔离。代码来源超时不阻塞项目、需求或知识卡片；刷新不能抹掉编辑草稿。
- 只展示经过规整的文本，不渲染仓库返回的任意 HTML；深链仅允许核验后的来源地址。

### 3.3 配置与请求边界

- 默认关闭；无仓库链接或未启用时不自动出网。启用只读来源不能启用旧 Webhook、后台同步、评审人写入、邮件或飞书通知。
- 首批仅固定 GitHub 公共 API 主机，不接受自定义 API URL、不跟随任意重定向、不读取环境中的既有 GitHub 凭据。
- 项目查看资格在查询前后核验；读取期间链接/revision 改变时丢弃旧结果。仓库改名/重定向需要明确提示，不静默修改绑定。
- 限制分页、响应大小、并发及总超时；不自动扫描全部项目或全部 PR。仅使用有界内存缓存、请求合并和限流退避，不新增缓存服务。
- 公共数据未认证请求共享出口 IP 限额，因此先采用主动加载和手动刷新。429/限流与无数据必须明确区分，限流期间不循环重试。

## 4. 本地验收方案

1. **离线回归**：默认关闭零出网；错误 URL、重定向、超时、限流、分页截断、恶意文本、缺失检查、PR head 改变、权限撤销、项目链接改变均使用本地可控响应验证。
2. **真实浏览器**：隔离测试账号完成绑定链接、查看列表、展开检查、跳转和返回；桌面/窄屏验证；另一个来源故障时其余页面可用。此层本地响应验收不冒充 GitHub 互通验收。
3. **真实只读互通**：独立的小型验证进程，仅访问明确选择的公共测试仓库及固定 API 主机，记录仓库/PR/SHA/来源时间；不带个人令牌，不创建 PR、不推送、不通知他人。保留默认本地网络守卫，不全局关闭隔离。该检查不等同于 D3 的完整交付验收。
4. **停止与回归**：停用后不再发新请求、清除来源缓存但保留仓库链接；已有登录、项目命令及受管空间回归通过。若无 schema 变更，不凭空新增迁移；若实现需要持久授权或新表，停止扩张并重新 review。
5. **资源清理**：仅停止本批创建的预览与测试资源，核对已有服务不变；验证完成后补独立实施记录、版本和证据。

# 第六批 Review：项目成员与权限边界

日期：2026-10-29。基线：`eb434a0` / `0.10.0-dev.0`。仅审查隔离的自部署套件，不操作现网。

## 1. 已核实的现状

| 领域 | 当前源码事实 | 对下一步的影响 |
| --- | --- | --- |
| 组织与项目身份 | 组织所有者 / 管理员来自统一身份；项目负责人和成员来自 Kick 项目记录 | 两种身份必须分别显示，不把组织管理员称为项目负责人 |
| 项目读取 | Kick 的列表、详情及操作历史对拥有应用访问权限的有效组织成员开放 | 目前没有私有项目；不能只加一个“私有”标签便宣称完成隔离 |
| 项目管理 | 现有负责人 / 管理员拥有管理入口，提交 / 审批 / 归档受阶段和 revision 限制 | 保留现有权限，不在信息展示迭代中改写授权规则 |
| 里程碑 | 后端逐项返回 `canChange`；管理视图已使用它，但待办详情仍重复计算成员 / 管理员条件 | 待办也应遵循同一个后端能力字段，缺失时不开放按钮 |
| Makit | 项目快照共享；当前需求仍有按名称归类与组织内读取语义 | 私有化必须覆盖需求列表、搜索、统计、直链、API 和 MCP，不能只过滤 Kick |
| WeKnow | 新受管空间同时检查当前项目资格与原生空间 ACL；既有空间保持独立授权 | 项目或组织管理身份不能被解释为已获得文档权限 |

证据位置：`apps/platform/server/workspace-store.mjs` 的 `rowToProject`、`rowToMilestone`、`list`、`get`、`audit`，以及 `apps/platform/src/workspace.js` 的里程碑渲染。WeKnow 的受管空间边界沿用第二、三批实施与本地回归；本批不更改其守卫。

待办列表目前主要返回分配给自己的里程碑，因此重复权限判断的正常触发范围有限。这里修正的是已确认的前后端判定差异，不声称发现过线上越权。后端权限检查始终保留。

## 2. 本批决定

1. 在已有项目详情中增加可分享 URL 的“成员与权限”只读视图；复用已加载的项目和会话，不新增接口、后台任务或第三方依赖。
2. 分别展示我的组织身份、项目身份、项目可见范围、Makit / WeKnow 独立授权边界、已有管理入口和成员名单。
3. 管理入口摘要与管理页共用同一展示函数；里程碑能力来自后端 `canChange`。页面展示不能替代命令授权。
4. 不新建维护者 / 观察者等业务角色，不转换已有空间、不改变可见范围，也不默认将管理员加入项目。
5. URL、刷新、撤权、键盘和窄屏继续使用现有机制；权限失效时清除名单和操作摘要。

“当前可用入口”描述现有页面入口，而不是另建一份完整服务端权限矩阵。例如审批期间新增里程碑的 UI / API 限制仍需单独确认业务口径，本批不扩大写入入口。

## 3. 项目转让的下一批候选设计

这是尚未实现的建议，不是已上线能力：

- 原负责人发起，接收人本人确认；组织所有权转让与项目负责人转让保持分离。
- 请求持久化，绑定项目 ID、原负责人、接收人、revision 和有效期；可取消、过期，重复提交返回原回执。
- 接收前重新核对双方有效身份、项目状态及当前版本；停用、归档或负责人已变化时不得沿用旧请求。
- 原负责人是否保留为项目成员，以及管理员是否可代发转让，实施前需确认。建议默认保留原负责人为成员，避免其尚未完成的里程碑失去归属。
- 接收人是否获得 WeKnow 原生角色必须明示；不得通过转让覆盖空间 ACL。相关权限未满足时应提前检查或明确返回部分完成状态。
- 需要持久状态时新增显式迁移和升级 / 中断恢复演练，不将安全状态塞入浏览器存储或审计文字。

## 4. 私有项目的前置条件

先完成稳定项目标识和全路径读权限，再开放可见性开关。必须覆盖 Kick、Makit、WeKnow 的列表、直链、统计、附件、API、MCP 和会话撤销；历史项目默认保持原可见范围，不能靠名字猜测并批量迁移。未完成这些条件前继续明确显示“组织内可见”。

## 5. 本批验收范围

- 单元 / 存储联测检查负责人、未参与项目的组织管理员、普通成员、审批和归档阶段。
- 实际浏览器检查只读名单、无额外 Makit 聚合读取、无审计写入、URL 刷新与历史、窄屏和键盘。
- 普通成员只看到已有入口；真实角色降级和账号停用后清除旧权限与名单。
- 复跑三应用主链路，核对现有运行服务；测试结束只停止本次资源。
- 本批不改变 schema 或迁移，不重做镜像升级，不将历史结果记作本批新验收。

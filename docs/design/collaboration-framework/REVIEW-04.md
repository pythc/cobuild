## 2. 已确认的问题

### R04-01 · P2：归档成功后，丢失响应不能重取原操作结果

- 位置：[workspace-store.mjs](../../../apps/platform/server/workspace-store.mjs)、[workspace.js](../../../apps/platform/src/workspace.js)。
- 当前归档 / 恢复直接执行 revision 检查、事务更新和同步入列，没有复用编辑 / 改名的 operation 与请求编号。
- 本地复现：第一次归档成功，响应没有 operation；再次提交同一请求得到 `409 revision_conflict`，但项目实际已经归档。
- 影响是用户无法区分“已成功、回包丢失”和“真正失败”，并且无法用同一操作编号追踪下游归档状态。
- 现有 revision 检查仍能阻止重复修改；这不是已发现的重复写入或数据丢失问题。

### R04-02 · P2：归档项目直链会在下一次数据刷新时切换对象

- 位置：[workspace.js](../../../apps/platform/src/workspace.js)。
- 首次加载优先选中 `?project=` 指定对象，但默认筛选仍为“进行中”；下一次加载根据该筛选判断选中对象不存在，切到第一个未归档项目。
- 使用真实页面逻辑和合成响应复现：归档项目 A → 再次执行 `loadProjects()` → 活跃项目 B。这里没有进行真实浏览器点击或截图验收。
- Kick 的项目选择 / 筛选也未写入 URL；Makit 项目页虽有项目参数，搜索和筛选仍只保存在组件内存中，见 [ProjectsPage.tsx](../../../apps/makit/client/src/pages/ProjectsPage/ProjectsPage.tsx)。后者是源码确认，尚未浏览器复现。

## 3. 下一批实施范围

| 顺序 | 小改动 | 复用方式 | 完成条件 |
| --- | --- | --- | --- |
| 1 | 归档 / 恢复接入持久命令 | 在已有动作注册表增加动作和事件；复用 operations、两应用原队列、当前权限与 revision 校验 | 同请求同输入返回原 operation；内容改变拒绝；恢复仍保留数据；下游未完成不误报全部完成 |
| 2 | 项目导航、筛选与刷新保留 | 使用 URL 保存项目和有效筛选；沿用现有请求代际、弹窗状态和路由 | 直链归档项目自动匹配筛选；刷新 / 前进 / 后退不换错对象；显式改筛选可清除不匹配选择 |
| 3 | 页面验收和证据更新 | 复用隔离测试运行器与已有浏览器测试能力 | 两个合成账号走完 Kick → Makit → WeKnow → 返回；更新当批记录，不套用旧浏览器成绩 |

实施细节：

1. 同一归档表单重试沿用请求编号，修改动作或输入再生成新编号。保留旧接口兼容；旧调用方缺少编号时不能声称拥有跨请求防重。
2. 操作回放、查询与重试均检查当前权限。获得回执不能绕过管理员降级或成员停用；归档中途某应用断开时保留当前部分结果。
3. 归档的项目版本与下游快照代际绑定。快速归档、恢复可以合并为最终状态，回执明确表示最终状态已确认，不伪称每个中间状态都执行过。
4. URL 只保存可分享的导航状态。编辑草稿留在当前表单，后台刷新不能替换表单或关闭弹窗；本批不加入跨浏览器草稿同步或持久保存敏感表单。
5. 无权、已删除、筛选不匹配和来源不可用分别处理。撤权不能以“保留页面状态”为由继续显示旧数据。
6. 如 store / 契约改动触发部署指纹，追加精确基线的审核计划和恢复验证；不复用旧摘要，也不将“无新表”解释成升级天然兼容。

## 4. 本地验收清单

- 归档提交后丢弃响应，再重试：同一 operation、单条业务修改、原项目 ID。
- 同编号不同输入、旧 revision、降权后回放、普通成员重试：明确拒绝。
- 中断一个下游、进程重启、归档后快速恢复：保留数据和回执，最终状态可收敛。
- 归档直链、活动项目切换、显式筛选、页面刷新和浏览器前进 / 后退：对象与筛选一致。
- 编辑时后台刷新、保存失败重试、角色撤销、来源超时：草稿与焦点合理保留，权限变化仍生效。
- 桌面 / 窄屏、键盘操作、表单错误与局部状态进行真实浏览器检查；不能仅靠 VM DOM 模拟判定 UI 通过。
- 按实际源码变化运行回归和精确升级验证；结束后只清理本次测试资源，不保留预览服务。

# 第一批实现：核心范围与项目操作契约

日期：2026-10-29。版本：`0.7.0-dev.0`。范围：D0 的运行范围收紧、D1 的首条实际业务链路。整体方案的其他阶段仍未完成。

## 1. 交付范围

| 改动 | 实际行为 |
| --- | --- |
| 核心模块注册 | `suite.json.modules` 只含 Platform / Kick / Makit / WeKnow；验证契约版本、依赖环、重复能力与应用归属 |
| 原始源码留存 | 非核心模块移到 `retainedModules` 元数据；配置不能启用，源码和原有数据不删除 |
| 资源标识 | 使用组织 UUID、应用 ID、资源类型、资源 UUID；显示名称不参与身份关联 |
| 通用操作记录 | 与业务变更使用同一 SQLite 连接和事务；保存操作、事件和投影绑定，任何一步失败全部回滚 |
| Kick 编辑及改名 | 已有编辑表单接入请求编号；专用改名端点也使用相同契约，保持项目 ID 不变 |
| Makit 同步回执 | 复用现有持久快照队列和单一消费者；回执区分本地已保存、等待同步、重试、阻塞、远端已确认 |
| 重试与权限 | 同编号同内容重试返回原操作；不同内容返回冲突；重试和查看回执均检查当前应用/项目权限 |
| 模块停用 | 非核心页面/API/MCP 保持不可访问；修复禁用招新仍创建其待办数据库的问题 |
| 部署边界 | 新操作库纳入 schema 指纹，继续拒绝未经批准的平台跨 schema 升级 |

这批没有加入第三方动态插件加载、任意脚本、低代码画布或额外中间件。外部扩展仍须独立进程和专门的权限契约；注册元数据不会执行代码或授予权限。

`packages/contracts` 不承担身份认证；`packages/operations` 不接受浏览器自报角色。授权来自 HTTP 层的当前身份与业务回调。内部调用也必须提供可信主体，不能因为持有服务密钥就得到项目编辑权。

## 3. 命令与回执

已注册动作：

- `kick.project.rename`：只修改项目名。
- `kick.project.update`：已有完整项目编辑操作，包括名称、简介、成员和链接。

对应事件为 `kick.project.renamed.v1` 与 `kick.project.updated.v1`，使用 CloudEvents 1.0 信封字段，存放在项目业务数据库。当前没有开放通用事件订阅 API，也没有把历史事件直接作为权限依据。

### 3.1 专用改名

`POST /api/workspace/projects/{projectId}/rename`，需要当前 Cookie、同源 Origin 和 CSRF 标记：

```json
{
  "requestId": "3e75003c-5937-4cde-b9a8-638ff0c95684",
  "revision": 3,
  "name": "新的项目名"
}
```

返回当前项目和 `operation`。`operation.revision` 是原操作提交后的版本；重试响应中的项目可能已经更新到更高版本，不能把两者混为一谈。

已有 `POST /api/workspace/projects/{projectId}/update` 支持可选的 `requestId`。新版表单会附带编号，网络失败后同一份内容重试复用编号，修改表单内容后生成新编号。旧调用方不传编号时由服务端生成，保留原接口兼容，但不能获得跨请求的防重保证。

`GET /api/workspace/projects/operations/{operationId}` 返回持久回执，仅当前项目负责人或有权管理员可读；成员停用、应用访问撤销或管理员降级后不会因知道操作编号而绕过权限。

### 3.2 回执语义

- `committed: true`：项目及操作记录已经在本地事务提交。
- `queued` / `running`：关联快照等待/正在同步。
- `retry_wait`：当前结果未确认，原消费者按原项目 ID 和代际重试。
- `blocked`：同步遇到需要处理的条件，允许有权用户通过已有重试入口继续。
- `succeeded`：本操作绑定的投影已确认；未启用 Makit 时没有投影步骤，表示本地命令完成。

当前投影消费者为 `makit.project-snapshot.v1`，回执的 `mode` 为 `snapshot-converged`，记录 `throughGeneration`、远端项目 ID 和 URL。连续改名可能合并为最新快照，**不表示每个中间名字都曾在 Makit 显示**。旧租约、旧回包不能确认新代际。

这批成功状态仅覆盖本地操作和已绑定的 Makit 快照，**不表示 WeKnow 空间已经改名**。WeKnow 的受管空间模式、同步改名及权限撤销属于后续 D1 工作。

## 4. 数据、启停与兼容

新增三张表：

1. `collaboration_operations_v1`：操作主体、请求编号、输入指纹、资源及提交版本。
2. `collaboration_events_v1`：不可变事件信封及操作关联。
3. `collaboration_deliveries_v1`：事件与消费者的代际绑定、状态及确认回执。

原 `projects`、`requirement_project_sync_v2` 和知识空间回执继续使用，不迁移到第二套业务库。操作记录、事件、投影绑定和原队列入列处于同一个业务事务。请求编号在组织和操作者范围内唯一；改变动作、资源或输入也会产生冲突。

兼容适配器仍可读取项目和处理原快照队列。重新使用新适配器时，会依据原队列的持久确认记录补齐操作回执，避免出现远端已完成而操作永远等待的情况。已确认回执不会被后续新操作重置。

核心模块开关仍在启动时生效，不支持热插拔。关闭 Makit 不会删除队列或数据；已有未完成步骤保留等待，重新启用后继续。排除业务模块的旧配置会明确报错，部署者应在副本上修改 `modules`；程序不会自动删数据或静默改配置。

**这不是已验证的旧镜像升级方案。** 新平台表已纳入部署 schema 指纹，现有迁移器仅支持已审核的 Makit 增量迁移，会拒绝本次平台 schema 变化。旧适配器兼容测试不等于旧二进制回退验收；不应绕过门禁或替换现有部署目录。正式升级须单独补齐平台迁移、备份、失败中断及回退矩阵。

## 5. 实际验证

| 检查 | 结果 | 边界 |
| --- | --- | --- |
| 根配置/身份/契约、项目存储/HTTP/同步/UI 回归 | 116 个用例通过 | 包含重复覆盖既有能力，不是 116 项新增功能 |
| 部署与迁移策略单元测试 | 35 个通过 | 未构建或发布 0.7 容器镜像 |
| 三项真实核心服务本地 HTTP 协作 | 140 个断言通过 | 空库、合成账号、专属本机数据库 |
| 原生集合持久化检查 | 7 个断言通过 | 不访问实验室数据 |
| 三服务重启验证 | 15 个断言通过 | 包含新的项目操作及同步回执 |
| 平台前端构建 | 通过 | 本次未做真实浏览器表单点击验收 |

针对性覆盖：同请求冲突、过期 revision、普通成员越权、管理员降级、应用权限撤销、事务中插入事件失败、提交后 `SIGKILL`、过期租约、旧回包、连续改名合并、旧适配器确认后的恢复、禁用模块不产生业务库。

首次运行发现禁用招新仍创建待办库，修复后已重跑相关测试；最终三服务测试通过并自动清理专属容器和进程。本次开始前的 11 个 SwanLab 容器 ID 与结束后相同，没有操作其服务或数据卷。

没有本次生产部署、真实消息外发、跨机器恢复、公开发行、长期压力和完整安全审计的验收结论。0.6 的 TLS 验证记录不能直接当作 0.7 的升级证据。

## 6. 自行 review 与下一批

本轮 review 后修复：

- 目录查询或读取请求体期间的权限变化：提交前重新获取身份并检查应用权限。
- 兼容适配器确认后，新操作记录仍排队：启动时从已有持久回执核对。
- 模块虽然不可访问却打开招新待办库：从存储初始化入口禁用。
- 新公共包的 schema 变化未被旧扫描范围覆盖：补入契约指纹和 schema 清单，拒绝未经审核升级。

下一批先补平台迁移与失败恢复，再推进受管 WeKnow 空间的改名、项目成员变化和权限撤销。旧全员共享空间不自动收紧权限；关联既有空间不自动改 ACL。之后再接项目统一界面、交付连接器和第三方扩展。

D0 的制品依赖裁剪尚未完成：原平台仍包含共享历史代码和依赖，不能将“运行不可启用”宣传为“镜像已完全剥离”。通用 PostgreSQL inbox、模块 draining、服务协议 v2、防重 nonce、外部扩展隔离与任意业务动作注册也仍是后续阶段。

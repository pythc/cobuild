# 第七批实现：项目负责人转让

日期：2026-10-29。版本：`0.12.0-dev.0`。源码基线：`cf37a89`。仅隔离的本地自部署核心套件。

## 1. 规则与实现

按 [Review 07](REVIEW-07.md) 和用户确认实现：当前负责人或组织管理员发起，由接收人本人确认；原负责人保留为普通项目成员。组织角色和原里程碑分配不变。首版接收人限现有有效项目成员，双方须保持启用并有 Kick 访问权限。停用负责人的接管不在本批范围。

- Kick “成员与权限”提供转让入口；接收人的工作台出现待办。发起、确认和取消均有明确动作，不使用邮件或外部机器人。
- 请求 24 小时有效。审批中、归档、待完善项目不能发起。接收时重查项目 revision、负责人、成员资格、发起者资格及应用访问；变化后显示失效，需要刷新并重新发起。
- 新增一张请求表；使用现有 SQLite、持久命令回执和事务。接收同时写入负责人、原负责人成员关系、revision、审计和 Makit 同步队列。请求编号绑定主体、动作及内容，重复提交返回原结果。
- 复用 Makit 项目快照队列，不新增同步进程；WeKnow 使用原空间及原生 ACL。转让项目负责人不等于转让空间所有权或增加文档权限。
- 请求状态读取不写库；过期按读取和提交时判断，无新增定时任务。撤销后旧请求的重放不能撤销后续新请求。

没有实施私有项目、细分角色、接收人任意选组织成员、MCP 转让工具或通用通知事件。转让采用专用持久回执和审计，未注册成通用操作事件。

## 2. 升级与恢复

追加 `platform/0002_project_transfers`，保留旧平台及 WeKnow 迁移摘要。迁移驱动验证已提交前缀与真实表结构；冲突时在 SAVEPOINT 内回滚，不改写旧历史。新计划 `core-project-transfer-v1.json` 限制精确四项 schema 持有文件变化。

本次实际升级基线是保留的 **0.9 运行镜像** `d795cbd40e38…`，不是新构建的 0.11 镜像；0.10 / 0.11 未改变 schema。最终候选为 `bee6ac9a9067…`。隔离演练包含追加迁移后应用启动失败、修复候选登记后再次中断、继续升级、拒绝旧二进制、重启和冷备份恢复。旧项目、登录会话、文档、附件及新写入保留；转让请求与独立接收人会话也保留，恢复后本人确认和重复提交均正确。

标准 Dockerfile 的无网络全量构建因缺少依赖缓存未完成，已停止。本次镜像保留精确基线的 Linux 依赖，核对依赖输入后覆盖重建的 Platform / Makit JS 与相关源码，未拷入 macOS 原生二进制。平台锁文件只存在 npm 元数据差异，包版本、完整性和依赖边一致；Makit 运行包沿用 Dockerfile 移除两项托管依赖的规则。**这证明本地候选的升级恢复，不证明全新环境的独立安装或公开镜像可复现构建。**

## 4. 自审与交付边界

复核了只有本人接受、管理员发起、接收人取消、旧请求重放、并发 pending、跨项目 ID、失效版本、成员移除、账号停用及发起人撤权。HTTP 在异步应用授权后再次同步核验参与者，参与者失效返回冲突，不把其他人的停用误当成当前操作者登录失效。迁移检查保留历史前缀，实际升级 / 恢复不使用人工伪造成功记录。

本次只有本机 HTTP、合成账号和隔离数据。测试服务和容器已停止 / 清理，原有 11 个运行容器 ID 与启动时间完全相同。没有操作线上、原始工程、真实外发、公开推送或留下常驻预览。TLS、跨机器、x86_64、长期容量及公开发行仍未验证；发行门禁保持 10 项阻塞、退出码 2。

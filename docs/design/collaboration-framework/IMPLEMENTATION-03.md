# 第三批实现：项目联动与受限修复

日期：2026-10-29。版本：`0.8.0-dev.0`。仅本地合成数据验证，不操作线上服务。

## 1. 范围与实现方式

本批继续使用平台现有 SQLite、Makit / WeKnow 的 PostgreSQL、已有同步任务及操作回执。没有新增数据库表、中间件、常驻服务或通用工作流引擎。原应用依然分别负责需求业务和文档业务。

| 能力 | 当前行为 |
| --- | --- |
| 项目改名 | Kick 提交一次修改，Makit 更新原项目快照，WeKnow 更新原受管空间名称 |
| 稳定关联 | 项目 ID、空间 ID、空间 slug、文档和附件不因改名重建 |
| 独立改名 | WeKnow 当前名称同时不同于已确认名称和目标名称时，停止覆盖并显示冲突 |
| 冲突处理 | 在 WeKnow 将名称对齐当前项目名，再从项目详情重试；不提供自动强制覆盖 |
| 手工关联 / 历史共享空间 | 继续沿用原权限与名称，不转换成受管空间 |
| 归档 | Kick 停止项目业务编辑；Makit 保留需求读取，拒绝新的需求写入；受管 WeKnow 空间暂停访问 |
| 恢复 | 保留原关联，重新同步，并按当前项目成员与原生空间权限判断访问 |
| 项目详情 | 分别显示 Makit / WeKnow 状态、关联链接、冲突及重试入口 |

归档后的受管空间是暂停访问，不是全员只读。此行为沿用第二批已验收的权限策略；不删除文档，也不修改历史共享空间的访问规则。

## 2. 同步一致性

WeKnow 原有队列的 `name` 用于保存最近确认的远端名称；申请创建时为申请名称。Native 模式才启用持续联动，保留旧 create-only 客户端行为。

业务修改与队列重置在同一平台事务中完成。任务携带当前项目版本、目标名称、归档状态和上次确认名称。WeKnow 在项目级事务锁内重新读取平台的权威项目状态；版本不同就重试当前版本。空间更新使用行锁，并保留稳定映射。

队列成功、失败和操作回执使用同一 SQLite 保存点。过期租约、旧任务结果不能把新任务标记为成功。改名操作同时包含 Makit 和 WeKnow 的投递状态，不再把单个应用完成误报为全部完成。

跨服务没有分布式事务：部分完成是可见状态，靠重试收敛。若远端改名成功但回执丢失，重试同一目标名不会重复创建；若期间又发生多次改名，无法确认的中间名称可能进入冲突状态，需要对齐名称后重试，不推断它一定是自动修改。

## 3. Makit 归档写入边界

原生记录存储在写入事务内查询 Kick 当前状态，覆盖界面、MCP、后台需求更新共用的记录路径。一次批量操作只进行一次状态查询，检查当前项目与拟迁入项目，识别历史名称，不能通过改名或清空项目字段绕过。

评论和验收项会解析其所属需求再检查项目。拒绝整批变更时，事务不保留部分写入。明确发生于写入前的归档拒绝使用专用错误类型，让后台任务显示“失败”，而不是“结果未知”。应用原有角色检查继续生效；服务检查只负责拒绝写入，不授予角色。

状态查询失败不放行写入。此检查会增加一次内部调用；没有做并发容量承诺，也不声称归档能撤销已经获准且正在提交的跨库请求。

## 4. 修复版本继续升级

新增命令：

```sh
python3 deploy/suite.py resume-upgrade /srv/cobuild/team --release release-fixed.json
```

替换版本必须满足：

1. 与 pending 候选使用同一精确迁移计划、来源镜像和 schema contract。
2. 所有 schema 清单文件、迁移执行器、迁移历史摘要完全一致。
3. PostgreSQL、Redis、网关镜像不变；仅应用运行时代码可以修复。
4. 修复候选经过预检后，原子更新 pending，并保留被替换候选记录。
5. 继续执行幂等迁移检查和启动验证；失败再次停止本部署，保留 pending。

修复成功后的候选链保存在部署目录 `last-recovery.json`。后续再次中断时，直接运行不带 `--release` 的 `resume-upgrade`，继续 pending 中已经登记的精确候选。

这不是任意代码降级、修改已提交 SQL 或替换数据库的入口。当前保守 schema 指纹包含持有 schema 的实现文件；若修复涉及这些文件，也必须另行审核迁移方案，不能用此命令绕过。

## 5. 本版本的发布门禁

数据库结构未变，但两份平台 store 文件的源码发生变化。`core-runtime-v1.json` 精确记录上批镜像到本批候选的这两份文件摘要，并要求保留核心迁移历史及执行器。它不接受任意文件或 DDL，也不替换之前的 `core-managed-v1` 历史计划。

基线仍是保留的 `cobuild-suite:managed-migration-candidate`；本批使用独立 tag `cobuild-suite:lifecycle-candidate`。完整备份先于切换。新的归档写入边界启用后，不自动退回缺少该检查的旧版本。

## 6. 验证与限制

最终结果与精确镜像、源码摘要记录在 `provenance/project-lifecycle-checks.json`。测试覆盖真实三服务改名、独立名称冲突、归档 / 恢复、后台写入拒绝、重启、坏运行时替换、继续恢复、旧文档与附件保留及冷备份恢复。

未开展本批浏览器视觉验收、跨机器迁移、真实断电、长时间压力测试；未公开推送、公开镜像或发布线上。不要把本地验证视为公开发行或生产验收。

# 部署与升级目标

当前没有可执行的整套 Compose；不要把历史单应用部署文件用于新团队。`config` 示例和 `suite.json` 是目标契约，不会修改现有后台或授权。

## 核心部署应包含

统一入口/反向代理、平台、Makit、WeKnow，以及各服务需要的数据库、队列和文件存储。数据库可共用一个 PostgreSQL 实例的独立库与角色；知识库任务队列等依赖按实际构建核对。平台既有存储边界先保留，不能为了统一而直接搬表或共用所有表的写账号。

默认每次部署服务一个组织。对外只公布必要的 HTTP(S) 入口；数据库、队列、内部回调和健康探测不需要暴露公共端口。真实域名、HTTPS 回调和 cookie 行为通过最终部署测试确认。

## 安装验收

1. 干净机器仅有 Docker / Compose 和必要的管理员配置。
2. 首次安装生成自己的 secret；不带固定管理员、不需要原作者账号。
3. 未配置飞书/邮件/GitHub/AI 时，核心可运行，且不会向外发送消息。
4. 创建项目、关联知识空间、创建需求、分配与交付可完成。
5. 重启保留账号与数据，日志不会输出 code、token、邮箱密码或正文附件。

## 升级与恢复

- 发行清单锁定服务镜像 digest、源码 revision、数据库迁移版本与兼容区间。
- 备份包括数据库、文件及部署者自己的私有配置；在隔离目录恢复验证。
- 升级先验证资源和健康，后台任务在候选实例关闭，正式切换只运行一套消费者。
- 停止超时必须尊重各服务实际退出行为；不能只靠镜像名判断服务已经恢复。
- 兼容回退保留已执行迁移与新写入；不得自动恢复旧数据库快照覆盖升级后的业务数据。
- 不支持回退的迁移须在执行前明确说明，并准备前向修复或完整停机恢复路径。

实际资源下限、镜像和命令在 S4 验收后补充。本阶段没有对任何服务器执行操作。
